## 1. Executive summary

**Current overall phase: Phase 3 of 6 — Core Development & Integration, at an estimated 30% overall completion.** Foundation hardening remains unfinished. This is an early core implementation, not a complete gym operating system or a production-ready attendance product.

The repository contains a React/Vite/TypeScript frontend, generated PWA assets, Owner sign-in and verification code, member registration/listing, plan maintenance, purchase creation/history, and membership payment recording/confirmation/rejection. These business flows exist in source; they were **not verified end to end against a running Supabase stack** in this audit.

Fresh checks passed: lint, TypeScript, production build including PWA generation, static security configuration, and 49 offline draft-review unit tests. Deno execution was blocked locally; the guarded database preflight was blocked by file-ACL access; the npm vulnerability audit failed to reach its advisory endpoint. These checks must not be described as passing. Earlier records report 38 passing Deno tests and a failing database foundation assertion; they are historical evidence, not fresh results.

The complete registration-to-access lifecycle is missing: registration creates a pending member; no approval operation exists; purchase creation requires an active member; payment confirmation stops at `pending_activation` without term dates. No public QR/check-in page, attendance endpoint, authoritative eligibility calculation, walk-in confirmation transaction, offline queue, reporting/export subsystem, or usable cash reconciliation workflow was found.

The most serious existing architecture issue is the mismatch between the intended restricted database executor design, migration ownership behavior, and security assertions. Drafts under `docs/drafts/` propose a remedy but are not applied migrations or verified runtime security.

**Next recommended development task:** review and approve the prepared ownership/executor foundation proposal and phase-aware security acceptance contract, including isolation and recovery requirements for synthetic validation. Then implement an approved forward migration in an isolated test environment. Do not proceed directly to Attendance or deploy the drafts.

## 5. Database and backend assessment

### Schema and migration consistency

The 24 migrations cover initial settings/members/Owner/audit, membership plans/purchases, ledger/allocation/corrections, walk-ins/attendance, PIN credentials/tokens/rate limits, cash reconciliation, audit-chain enforcement and server-only Owner RPCs. The final source-defined inventory is 22 application tables (21 private plus `public.gym_settings`); an intermediate enrollment limiter table is intentionally replaced by the rolling-event table. Later migrations replace earlier RPC bodies, so evaluating only the first definition gives the wrong behavior.

Foreign keys link allocations to purchases/walk-ins, receipt allocation is unique per payment, positive numeric PHP amounts are constrained, and dated membership intervals have a GiST overlap exclusion. RLS enablement and browser privilege revocations appear for all final application tables. These are meaningful foundations, not a completed lifecycle.

Fresh read-only offline parsing passed SQL grammar checks for all 24 migrations using cached PostgreSQL 17 and 18 parser bindings, after removing leading UTF-8 BOMs **in memory only**. PostgreSQL 18 procedural parsing also accepted all 26 individually extracted PL/pgSQL bodies. This proves syntax coverage, not relation/type resolution, extension availability, authorization or migration execution. Four original files contain a BOM: `20261030140000_owner_create_pin_enrollment_token.sql`, `20261030150000_member_pin_enrollment.sql`, `20261103080000_owner_membership_plans.sql`, and `20261103100000_owner_create_membership_purchase.sql`. Raw parser input refused those markers; actual migration-tool encoding handling remains Not Verified. No migration bytes were changed.

Important gaps:

1. No approval operation assigns `approved_at`. Registration inserts pending members; purchasing requires `members.status = 'active'`. The supported UI journey cannot complete this transition.
2. `owner_confirm_membership_payment` updates the purchase to `pending_activation` and writes event/allocation/audit records; it does not calculate or set entitlement dates.
3. Active membership with null dates remains possible under existing table checks. Dated periods are not checked for the exact calendar-month rule or consecutive renewal. A trusted writer can create states beyond the guarantees of the current RPCs. This is a source invariant gap; it does not prove browser access to those writes.
4. Walk-in request expiry/fee immutability, paid eligibility and attendance validity are not implemented as trusted operations.
5. No correction transaction connects payment confirmation voids to membership/attendance invalidation and retained history.
6. The later payment guards restrict transitions to recorded-to-confirmed/rejected; the foundation's void status/correction tables do not themselves make correction executable.
7. There is no implemented received-money review/reallocation path suitable for unmatched/underpaid receipts or drawer totals.

A historical November 6 record reports all 24 migrations applied to the guarded native PG18 test database, payment catalog assertions passed, and foundation assertions failed at `public.gym_settings is not owned by gym_data_owner`. **No migrations or database assertions ran successfully during this audit.** The protected preflight failed on `Get-Acl`; no database connection was attempted after that refusal. Fresh migration replay, actual catalog consistency, concurrency, RLS behavior, PostgreSQL 17 compatibility and hosted migration drift are **Not Verified**.

### Backend service boundary

Existing Edge entrypoints: `owner-status`, `owner-register-member`, `owner-create-pin-enrollment-token`, `member-enroll-pin`, `owner-list-members`, `owner-list-membership-plans`, `owner-save-membership-plan`, `owner-create-membership-purchase`, `owner-list-membership-purchases`, and `owner-membership-payments`.

Owner handlers verify the access token using Auth `getUser`, derive the actor ID server-side and call server-only API RPCs; SQL checks active Owner status for privileged business operations. The public enrollment endpoint uses a one-time token rather than a member Auth session. `verify_jwt = false` on configured handlers is not by itself an authentication bypass: internal validation is material. Nevertheless, not all ten endpoints have explicit per-function config entries, and their deployed gateway settings need verification rather than assumptions from a successful frontend build.

Not configured/proven as complete application services: check-in/eligibility, registration approval, renewal, walk-in operations, payment corrections, receipt review, drawer operations, reporting/export, offline synchronization, backup/restore and emergency-access controls. No payment provider integration is implemented or required for the existing manual confirmation design.
