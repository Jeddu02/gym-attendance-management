## Staging deployment order and recovery limits

1. Obtain explicit staging write authorization for the reviewed 13 core artifacts and the no-backup execution plan. Confirm staging identity, named artifacts, SHA-256 manifest, baseline history and quiet window.
2. Apply one reviewed artifact at a time using the verified customer `postgres` connection. Each file owns its transaction. Check the expected catalog and resulting history entry after each step. A failed transaction should roll back that file. Earlier committed files remain in effect. If a connection drops or the result is ambiguous, stop and reconcile the catalog and history before attempting anything further. Recovery after a committed step will require a reviewed forward correction. No backup-based restore is part of this plan.
3. Pass the executor, final security and browser-role gates on the actual staging catalog. Recheck data counts and Auth/Data API settings. Use staging-only secrets and enable only approved flows.
4. Deploy verified functions for the scoped Owner and member flows and connect the PWA to staging. Test Owner login and non-owner denial, registration, membership purchase and renewal, payments, PIN enrollment and recovery, member QR attendance and duplicate rejection, provisional offline review, cash and reports. Verify the current mobile UI and loading/error paths through the staged backend. Add hosted walk-in acceptance after its separate release gates pass.
