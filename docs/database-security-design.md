# Proposed database and security design

**Status:** proposal for review. This document describes a future schema and
security boundary; it does not create migrations, policies, RPCs, or workflows.

## Scope and invariants

- One gym location initially. Defaults are `Asia/Manila` and `PHP`; approve both
  before creating settings or accepting transactions.
- Supabase PostgreSQL stores operational data. Supabase Auth authenticates the
  Owner only. Members have no Auth account, dashboard, or member login.
- Anonymous visitors use a public entrance page. Its check-in request is
  verified by a server endpoint and a narrowly scoped database operation.
- The browser is untrusted. Authorization, payment state, entitlement, date,
  role, and duplicate decisions are calculated on the server.
- There is no checkout, refund, or complimentary-membership concept.
- Never grant access before member registration approval and confirmed payment.
- The Owner is the only management-system user. No manager/front-desk accounts
  are in the initial release. The Developer's technical identity and ordinary
  member identity are separate; neither grants Owner access.
- A walk-in record is valid only after the Owner confirms actual payment and a
  trusted server operation validates and commits payment plus attendance.
- An Owner-recorded offline check-in is a provisional claim until the server
  validates it; client time is not proof of historical attendance.
- A developer or development automation has no automatic access to live member
  data.

## Proposed entities and relationships

All primary keys are UUIDs unless a compact sequence is more appropriate for an
append-only audit stream. Foreign keys should use `ON DELETE RESTRICT` for
financial, attendance, audit, Owner, and membership history. Operational
records are corrected or retired through audited state changes; they are not
hard-deleted. Use `created_at`/`recorded_at` as `timestamptz` generated by the
database. Money is integer minor units plus an ISO currency code; never use
floating point.

### Important constraints and indexes

- Generate random, non-sequential member codes with enough entropy to resist
  enumeration. Store encrypted display value and a unique keyed HMAC for lookup;
  do not expose a member-code listing endpoint. Store E.164-normalized phones
  encrypted and uniquely index their keyed HMAC for the initial one-member-per-
  mobile policy. Use separate, versioned server-managed HMAC/encryption keys.
  If household sharing is later approved, revise lookup/rate-limit design before
  migration rather than silently accepting ambiguous phone matches.
- `membership_plans.term_months = 1`, purchase snapshot `term_months = 1`,
  `membership_plans.price_minor > 0`, purchase snapshot `price_minor > 0`,
  payment `amount_minor > 0`, and walk-in fee `> 0` make complimentary access
  unrepresentable. Currency must match the configured gym currency unless a
  future multi-currency decision is approved.
- Index every actual FK used in joins: purchase, entitlement, payment,
  attendance, correction, reconciliation, application, and Owner actor
  references. A polymorphic `entity_type/entity_id` is not a foreign key and is
  not used for authoritative audit subjects; typed subject FK rows are defined
  in the schema contract. Add indexes for member/status lookup,
  `gym_local_date`, `server_received_at`, payment targets, and Owner checks.
- Enforce **at most one valid member check-in per member per gym-local date**
  with a partial unique index on `(member_id, gym_local_date)` where
  `kind = 'member' AND status = 'valid'`. A server transaction locks the
  member row, checks eligibility, and
  inserts. The unique index is the final concurrency guard; return a safe
  duplicate outcome on conflict. Request idempotency keys make retries return
  the original outcome.
- Member check-in eligibility is evaluated in one transaction from the
  currently configured gym timezone. The server writes the UTC instant and
  `(server_received_at AT TIME ZONE gym_settings.time_zone)::date`; clients do
  not submit the authoritative date.
- `expires_on` is **inclusive through the entire local expiry date**. A
  membership is in its date window when `local_date >= starts_on AND
  local_date <= expires_on`. Its exclusive instant boundary is local midnight
  on the day after `expires_on`, converted using the configured IANA timezone.
- With `Asia/Manila` (UTC+08:00), local midnight is 16:00 UTC on the prior
  UTC date: `2026-06-14T15:59:59Z` is June 14 local; `2026-06-14T16:00:00Z`
  is June 15 local. An entitlement expiring June 15 is valid through
  `2026-06-15T15:59:59.999Z` and expires at `2026-06-15T16:00:00Z`.
- Finalized Option A: advance a term start/activation date one calendar month,
  clamped to the target month's final date; that date is the next-term start,
  and inclusive expiry is the previous date. Jan 31, 2027 -> Feb 28 next-term
  start, Feb 27 expiry; Jan 31, 2028 -> Feb 29 start, Feb 28 expiry. Feb 28 in
  a normal year -> Mar 28; Feb 29 in a leap year -> Mar 29. Store these as
  `Asia/Manila` dates separately from UTC timestamps.
- Partial unique indexes can enforce one pending member application per member
  and one open cash session where applicable. Unique effective-payment
  projections enforce at most one full confirmed membership payment per
  purchase and one confirmed walk-in payment per request. Lock the target row
  and update the projection with append-only payment events.
  Pending payment-correction
  proposals are serialized by locking the payment row and checking for an
  undecided proposal in that transaction; decision state lives in append-only
  events, so a partial index over that event state is not available without a
  separate mutable projection.
- The initial `owner_access` is a singleton. Bootstrap is controlled,
  identity-bound, one-time, audited, then disabled. Recovery/revocation is
  Owner-controlled and must not permit public re-enrollment.
- `request_idempotency` has a unique `(operation, idempotency_key)` constraint;
  offline receipts separately have unique `(owner_user_id, idempotency_key)`.
  A stored keyed fingerprint binds a retry to the original request without
  retaining sensitive request fields.
- All state transition and audit writes occur together in a transaction. Use
  `CHECK` constraints for row-local invariants and constrained RPCs/triggers
  for cross-table rules.

## State transitions

| Entity | Allowed transitions | Guard |
| --- | --- | --- |
| Member registration | `pending -> approved` or `denied`; `approved -> suspended`; `suspended -> approved` | Owner action with actor, reason, and audit event. A denied registration requires a new reviewed application. |
| Purchase | `pending_payment -> paid`, `paid -> payment_review` after an approved correction | Paid only when registration is approved and exactly one server-confirmed effective payment equals the immutable purchase amount. Correction/void-in-error replacement is separately audited. No installment or cancellation action/state. |
| Entitlement | Created active on eligible activation; active -> suspended -> active only through security review | Option A finalized: one calendar month with end-of-month clamping; inclusive expiry is prior date. Early renewal begins the day after existing expiry; lapsed renewal begins on new activation. Access lasts through expiry; then a new approved purchase and one full confirmed payment are required. No cancellation, freeze, or expiry override. |
| Payment receipt | `recorded -> confirmed -> confirmation_voided_in_error`; `recorded -> rejected` | Append-only actual-receipt verification events. Proposed non-additive reports separately show verified money received, unresolved receipts, approved underpaid receipts, qualifying full payments, and an operational confirmed membership-payment total. A receipt counts once as received; only its verified subset is included. Approved-underpaid is a subset of received, never qualifying payment/income/access. Owner/accountant must confirm accounting labels/treatment before live financial reporting. No refund transition. |
| Payment allocation | `proposed -> approved_full/approved_underpaid/rejected -> voided` where an audited Owner correction requires it | One immutable whole-receipt assignment to one typed target, Owner reason/evidence; at most one current allocation per receipt. `approved_underpaid` is traceable and reported once as received money, but does not reduce amount due, qualify as membership income/access, or combine into an installment. A separate later exact full receipt may become the only effective payment without voiding the underpayment. |
| Payment correction | `proposed -> approved/rejected`; approved case cannot be edited | Owner-only approval, reason/evidence, append-only decisions; one open case per original receipt/allocation. Correction preserves actual receipt and appends a corrected allocation if appropriate. |
| Member check-in | `provisional -> valid`, `duplicate`, or `rejected`; terminal outcomes do not transition | Trusted server validates member PIN proof, registration, paid entitlement, local date, and duplicate constraint. |
| Walk-in request/check-in | `provisional -> valid` only on verified exact-fee allocation; `valid -> payment_review` when its confirmation is voided in error; otherwise `provisional -> expired/rejected` | Owner confirms actual receipt; request/receipt/allocation/attendance transition is one transaction and has at most one effective confirmed allocation. Expired request is never revived. |
| Offline submission | Provisional claim to one terminal server outcome | Authenticate Owner at sync; re-check current eligibility/date/duplicate under lock. Client time is not historical proof. Same-key retry returns saved result. |

## Authorization, RLS, and service boundaries

### Confirmed initial authorization model

- **Owner:** only management-system user. Verify the current authenticated
  identity against private `owner_access` for every protected operation. No
  user metadata/client claims grant privileges. One-time bootstrap is controlled
  and disabled after use.
- **Anonymous:** no direct table access. Only fixed public member-check-in and
  Owner-approved walk-in-request operations may be invoked; responses reveal no
  member/payment details.
- **Developer:** no management identity, production DB role, project secret, or
  routine live/restored data access. Source/deployment access is separately
  bounded and Owner-approved. The Developer's member identity is ordinary only.

### Supabase enforcement

1. Enable RLS on every Data API exposed table; default to no policies and no
   `anon` grants. Revoke broad table privileges. Test direct REST/SQL attempts
   as `anon`, the Owner role, and service identities.
2. Base Owner identity on verified `auth.uid()` plus private `owner_access` queried
   server-side. Do not trust user-editable `user_metadata` or stale role claims
   for authorization. Role changes take effect on the next protected request.
3. Client writes to protected business tables are not direct inserts/updates.
   Use narrow RPCs/Edge Functions for registration approval, payment
   confirmation/correction, membership activation/renewal, security suspension,
   check-in, cash reconciliation, role changes, and PIN verification. Each
   operation checks caller identity/role, validates state transitions, writes
   audit history, and commits atomically.
4. If an Edge Function uses the Supabase service-role secret, that secret exists
   only in server-managed function secrets. Never send it to React, a `VITE_*`
   variable, source control, browser storage, logs, or developer automation.
   A service-role call bypasses RLS, so each function must independently
   authenticate and authorize; expose only fixed operations, never generic SQL
   or arbitrary table access.
5. Keep PIN hashes, rate-limit rows, encryption keys, and internal audit tables
   in a non-exposed/private schema or revoke all Data API privileges. For views,
   use invoker security where possible; every definer function uses a fixed
   `search_path`, fully qualified names, minimal grants, and explicit caller
   checks.
6. Realtime is optional and only for authenticated Owner views whose underlying
   rows have tested RLS. Do not publish PIN, phone, payment details, correction
   payloads, audit metadata, or public member lookups. Realtime never confirms
   payment or attendance.

## Member identity and PIN design

- Member ID or registered mobile number is an identifier, not proof of
  identity. Both paths require the member-specific PIN.
- Store only an Argon2id verifier with a random per-PIN salt and a server-only
  pepper/key version. Choose memory/time parameters for the production runtime
  and benchmark them before launch. Do not log, echo, cache, or persist the
  submitted PIN. The hash and pepper never leave the verifier boundary.
- A short numeric PIN has low entropy even when hashed. Recommended starting
  default is a random 10-digit numeric PIN (do not permit a shorter PIN without
  explicit security review); rate limit atomically
  by keyed identifier and network/device bucket, progressively lock out
  repeated failures, and audit resets. Do not use a permanent lockout that
  enables denial of service. Tune thresholds after abuse testing.
- Unknown Member ID, unknown mobile, wrong PIN, unapproved registration,
  unpaid/expired membership, already checked in, and throttling return the same
  public error shape and non-revealing wording. Never return whether an
  identifier exists, its member name, membership status, or payment status.
- For unknown identifiers, verify against a server-held dummy Argon2id verifier
  so the missing-member path does not skip the expensive PIN check. Keep the
  response body/status uniform and measure timing distributions during tests;
  never claim perfect constant-time behavior across database/network paths.
- Rate-limit before expensive hashing and apply IP/network throttling plus
  identifier throttling. Use only trusted edge request metadata; do not trust a
  client-supplied IP header. Keep throttle keys pseudonymous and short-lived.
- PIN reset requires an Owner-authorized identity-verification procedure and an
  audit record. Only the Owner performs the reset server-side. Never reveal or send
  the existing PIN. Accept the PIN as a string so leading zeroes are retained.
  Paid SMS is not required.

## Offline and payment rules

- The Owner PWA may queue a minimal, encrypted provisional envelope with an
  idempotency UUID, Owner ID, device installation UUID, member reference, and
  client-observed time. Do not cache PIN, phone, member profile, payment data,
  or membership status. Use managed device protection and clear the queue after
  a final outcome.
- Member/public QR check-in requires internet. It does not queue or claim
  success offline. Only Owner can create offline provisional submissions with
  unique operation IDs and idempotent synchronization.
- Client time is untrusted and cannot prove historical presence. Server receipt
  time is authoritative for valid current-date check-ins. The 24-hour window is
  a provisional review/triage threshold only. Owner may attest present physical
  attendance, but the server still checks eligibility and duplicates. Old,
  suspicious, conflicting, or expired claims remain visible until the documented
  Owner resolution path; never silently discard or approve them.
- Revalidate Owner authorization is still active, member approval, paid entitlement,
  inclusive expiry, local date, and duplicate status at sync. Concurrent online
  and offline sync requests converge through the same unique index.
- Use server receipt time for authoritative local date on sync. The 24-hour
  window routes claims for review only; it cannot prove claim age or historical
  attendance. A valid row uses the current server date. Configure the threshold
  boundary, clock tolerance, retries, queue expiry, and resolution path before
  operational use.
- A payment record means actual funds were received. Confirmation is an
  authorized event, not client state or an unverified provider callback. A
  membership becomes accessible only after registration approval and exactly
  one full confirmed payment equal to the purchase amount. No partial/installment
  path exists. An offline claim cannot confirm payment.
- Public QR may create an expiring provisional walk-in request with a server-
  assigned opaque ID and fee snapshot. Only Owner confirmation of actual receipt
  while unexpired can atomically make its payment and linked attendance valid.
  Expired requests are never revived; a new request uses a new ID/current fee.
  Do not add a walk-in membership or complimentary path.
- Payment receipt rows are immutable. The proposed correction ledger distinguishes
  a false confirmation from a replacement record for the same actual receipt.
  A voided confirmation is excluded from effective payment; a replacement is
  separately linked and the original cannot also count. Nothing represents a
  returned payment. Unmatched receipts remain in review and are not confirmed
  income. Proposed reporting detail: a verified, correctly allocated
  underpayment is counted once as received money but separately from confirmed
  membership income; it cannot satisfy purchase eligibility or be combined as
  an installment. Preservation/no-installment/no-auto-access are Owner-approved;
  confirm the income classification with Owner/accountant before live reporting.
  No receipt is discarded or automatically converted to access/refund.
- Payment confirmation is a server-side operation. Membership cancellation
  and expiry overrides are not available in the initial release. A security
  suspension is a separate Owner-only, reasoned, audited control; it must not
  rewrite paid entitlement dates or serve as a cancellation mechanism.

## Audit, privacy, and live-data safeguards

- Append audit events transactionally for approval, denial/suspension, member
  check-in outcomes, payment record/confirmation/correction, purchase/entitlement
  activation/renewal, cash reconciliation, settings changes, PIN
  reset, and Owner access changes. Include actor, UTC time, request ID,
  entity, action, and required reason for sensitive corrections.
- Revoke update/delete on audit and original financial tables from app roles;
  require a database trigger that rejects mutation. Append a canonical event
  hash linked to the previous event hash and periodically anchor a signed chain
  digest in owner-controlled storage. This detects application-level history
  edits; a database superuser can still rewrite database contents, so the
  external anchor and restricted break-glass access are part of the control.
  Avoid full before/after JSON dumps.
- Encrypt contact/name PII at the server boundary and index mobile lookup with a
  keyed HMAC. Keep keys in server-managed secrets, version and rotate them, and
  audit authorized decryption. Apply retention/deletion rules only after legal
  and business requirements are decided.
- Do not cache sensitive records in the service worker, emit them to analytics,
  or include them in errors. Restrict reports/export and log redaction.
- Development uses synthetic fixtures only. Developer accounts/automation are
  not members of the production Supabase project, hold no production secret,
  and cannot run queries against live member tables. Any future emergency
  operator access must require owner approval, be time-limited, read-scoped,
  recorded in an access log, and separately authorized; no automatic developer
  access is permitted.

## Transaction pattern overview

All protected operations use a single database transaction, reserve the
operation idempotency key, recheck current server-side state, and append audit
before commit. The exact canonical lock order and operation lock sets are
specified in **Proposed canonical transaction and lock protocol** below; that
protocol supersedes any ordering implied by earlier abbreviated examples.

## Owner-only terminology and confirmed-rule alignment

The initial release has one management actor: the Owner. There are no manager
or front-desk accounts. Any legacy `staff` actor label or “staff view” wording
must be interpreted as Owner-only or removed during schema implementation; it
must never become a grantable role. The Developer's technical identity remains
separate from their ordinary member profile and has no routine live-data access.

Month arithmetic and activation examples are Owner-confirmed. Add one calendar
month to the activation/term-start date, clamp to the target month's final day,
and use the preceding date as inclusive expiry (Jan 31 -> Feb 28/29 next-term
start, expiry Feb 27/28; Feb 28 normal year -> Mar 28; Feb 29 leap year ->
Mar 29). Activation is the later gym-local date of approval and full confirmed
payment. Early renewals are directly consecutive; no arbitrary future prepaid
or overlapping periods. Full payment and registration approval are prerequisites.

All offline submissions are provisional claims. The confirmed 24-hour boundary
is a review/triage signal only; server receipt time controls any current-date
eligibility and device time alone cannot prove historical attendance. Queue
expiry and stale-claim resolution remain operational details. Walk-in requests
use a stable request ID and immutable fee snapshot. A single transaction
confirms actual receipt, makes one effective payment pointer, validates one
attendance record, and appends audit history. Expired requests cannot be
revived; request lifetime remains an operational setting.

## Proposed canonical transaction and lock protocol

This order is a design proposal, not a tested implementation. Every protected
mutation uses one database transaction and follows this global order, skipping
classes not needed by that operation. When multiple rows in one class are
needed, lock them by ascending primary key:

0. Reserve `request_idempotency(operation, actor_scope, key)` by unique insert;
   bind the keyed payload fingerprint. A conflicting insert waits for the first
   transaction. Same fingerprint returns its committed result; changed
   fingerprint fails without executing the operation.
1. Lock the singleton `gym_settings` row `FOR SHARE` to pin timezone/currency/
   configuration version. Settings changes take `FOR UPDATE`.
2. Lock affected member rows in ID order. This serializes eligibility,
   membership sequencing and public/offline daily check-in decisions.
3. Lock membership purchase rows in ID order.
4. Lock entitlement rows in ID order.
5. Lock walk-in request rows in request-ID order.
6. Lock cash drawer session rows in ID order.
7. Lock receipt rows in ID order.
8. Lock allocation and payment correction/projection rows in ID order.
9. Lock attendance rows and the applicable `(member_id, gym_local_date)`
   decision key in stable order. A missing row is not lockable; uniqueness
   constraints arbitrate insertion races.
10. Lock reconciliation snapshots/adjustment streams in ID order.
11. Lock affected `audit_chain_heads` by stream key order, append audit events,
    then persist the idempotency result and commit.

No external network call or human confirmation occurs while locks are held.
The Owner confirms actual receipt before invoking the operation; the transaction
rechecks the current request/payment state and snapshots. A transaction that
cannot append its required audit event/chain head, store its idempotency result,
or complete all business changes aborts as a unit. Retry only serialization
failure/deadlock SQLSTATEs with the exact same idempotency key and fingerprint,
using a bounded server retry policy; after exhaustion return a retry-safe error.
Never blindly retry a different payload or report success before commit.

Required uniqueness remains even with row locks: idempotency scope/key;
membership purchase effective-payment target and allocation pointer; walk-in
effective-payment request and allocation pointer; one current allocation per
receipt; replacement original and
replacement links; one open correction per original; one attendance per
member/local date; one walk-in attendance per request; one open drawer per
drawer code; one reconciliation per drawer session; and one correction
  adjustment per correction and relevant receipt. These constraints protect
against missed locks, alternate write paths, and concurrent transactions.

### Operation lock sets and atomic effects

- **Membership purchase/payment confirmation:** idempotency, settings, member,
  purchase, existing entitlement(s), cash session when cash, payment,
  correction/effective projection, audit. Verify Owner JWT/active `owner_access`,
  exact full PHP snapshot, actual receipt evidence, registration approval,
  idempotency, and whether this is an early consecutive renewal or a lapsed
  term. Derive activation using server time converted to `Asia/Manila`; never
  accept a client date. Create payment event, effective pointer, purchase state,
  entitlement and lifecycle/audit rows together.
- **Early renewal:** use the same lock set through entitlement. Require a full
  confirmed payment for the new purchase. Start exactly the day after the
  latest paid entitlement's inclusive expiry; lock the member before deriving
  this date and reject non-consecutive/overlapping terms. A lapsed purchase
  starts at its server-derived activation date. One purchase grants one month.
- **Member public check-in:** idempotency, settings, member, purchase,
  entitlement, effective payment, attendance decision key, audit. Verify PIN
  and rate limits in trusted server code; lock/recheck the credential version,
  approval, suspension, effective full payment, active date interval and current
  Manila date. Insert with the server-derived date. The unique index is final
  duplicate arbitration; on conflict return the same generic public outcome.
- **Walk-in confirmation and attendance:** idempotency, settings, request,
  cash session if applicable, receipt, allocation, payment/correction projection,
  request attendance, audit. Require the request be provisional and unexpired
  at server transaction time; its fee-version/amount/currency snapshot must
  match. Confirm actual receipt and exact full-fee allocation, effective-payment
  pointer, request validity, attendance referencing that request/allocation, and
  audit commit together.
  If any check or audit fails, none of those changes commit. No reverse FK from
  request to attendance is used.
- **Payment correction:** idempotency, settings, member/purchase/entitlement if
  membership-targeted, request if walk-in-targeted, cash session, source receipt,
  original/replacement allocations, correction/effective projections, impacted
  attendance, and reconciliation/adjustment only if a source-fact correction
  changes physical cash after close; audit. Recheck actual receipt evidence
  and exact target snapshot; append the correction decision and void/replacement
  events; switch effective payment once; recompute eligibility; record impacted
  attendance without deleting it; create a post-close adjustment only when the
  source-fact correction changes expected physical cash.
  Never create a refund or cash movement. All effects and audit commit together.
- **Cash reconciliation:** idempotency, settings, drawer session, its verified
  actual cash receipt rows in payment-ID order (including unallocated receipts
  physically held; excluding receipts not received or known voided),
  reconciliation, audit. Drawer cash is distinct from confirmed-income status
  and the effective-payment pointer that grants membership eligibility. The
  payment confirmer and close operation both lock drawer before payment rows,
  so the set is stable. Closing stores an immutable snapshot. Later approved
  corrections append separate linked adjustments only when the corrected source
  receipt fact changes physical cash expected (false cash receipt or corrected
  verified cash amount). Changing only the allocation target has no
  physical-cash effect. Each adjustment links one correction and receipt to
  one closed reconciliation for the same session, and to the exact Owner who
  approved that correction; it is unique per correction and retries cannot
  append another. Correcting GCash or bank does not affect drawer totals.
  Cash/non-cash method reclassification is held for explicit Owner resolution
  and has no automatic adjustment. Original events and the close snapshot
  remain immutable.
- **Offline sync:** idempotency, settings, member, purchase, entitlement,
  effective payment, attendance key, audit. Recheck active Owner JWT at sync,
  current local date and current eligibility. Client time only selects a review
  path. Duplicate, stale or ineligible claims remain visible; no historical
  valid attendance is created from a device timestamp.

The `Asia/Manila` date is calculated inside the trusted transaction from server
time and the locked settings version. Expiry remains inclusive through
`expires_on`; access is false starting the next local date. Membership and
attendance decisions lock the member before purchase/entitlement/effective
payment rows so a concurrent correction cannot leave a check-in authorized by
a payment being invalidated.

## Proposed Supabase grants, RLS, and trusted-function contract

This matrix is the proposed default-deny contract. Base tables are not directly
writeable by `anon` or `authenticated`; Owner reads use restricted views/RPCs.
All tables have RLS enabled if exposed through the Data API, with no permissive
catch-all policy. Private schemas are not exposed through the Data API.

For Owner-readable base tables, the only SELECT policy is scoped to
`authenticated` and requires `auth.uid() IS NOT NULL` plus an active row in
private `owner_access` whose `auth_user_id = auth.uid()`. Do not use
`user_metadata` or client role claims. No `anon` policy permits table
SELECT/INSERT/UPDATE/DELETE, and no Owner base-table DML policy is granted.
Safe read views expose only minimum required columns and retain caller RLS.
Use exactly two named `NOLOGIN`, `NOSUPERUSER`, `NOBYPASSRLS` function-owner
roles: `gym_public_executor` and `gym_owner_executor`. The private PIN verifier
is a narrowly scoped function owned by `gym_public_executor`, with only its
required credential/limiter access; it is not a third role. Neither executor
owns tables, can be assumed by `anon`/`authenticated`, or inherits a role that
can bypass RLS. A separate non-login `gym_table_owner` owns private objects
and is not a request-function owner. Revoke schema/table/function privileges
from `PUBLIC`; grant only required table privileges and RLS policies targeted
to each executor. Force RLS on private business tables. The public executor
never receives Owner operations; Owner functions independently verify
`auth.uid()` and active `owner_access` on every request.

| Table group (all named tables) | `anon` | authenticated Owner | trusted function executor |
|---|---|---|---|
| `owner_access`, `gym_settings`, `gym_setting_events` | No table grants; bootstrap HTTP operation only | Settings/view read only; no direct writes | Owner bootstrap/recovery validates one-time capability; settings changes require active Owner |
| `members`/`member_profiles`, `registration_applications`, `registration_decision_events`, `member_privacy_events` | No table read/write; public registration/check-in endpoints only | Minimum operational reads; mutations through Owner operation | Public check-in lookup is exact identifier+PIN only and returns generic result; registration/profile operations validate Owner |
| `member_pin_credentials`, `member_pin_tokens`, `pin_attempt_buckets` | No grants | No table read/write; request setup/reset operation | PIN verifier/token/rate functions only; never return PIN/hash/token hash |
| `membership_plans`, `membership_purchases`, `membership_entitlements`, `membership_lifecycle_events` | No grants | Read through limited views; create/approve/renew/security suspension through Owner operation | Enforce approval, complete payment, dates and consecutive-term invariant |
| `payment_records`, `payment_allocations`, `payment_allocation_events`, `current_receipt_allocations`, `payment_events`, `payment_corrections`, `payment_correction_events`, `payment_replacements`, `membership_payment_effective`, `walkin_payment_effective` | No grants | Minimal read; verify, allocate, confirm, correct only through Owner operation | Preserve unallocated receipts; exact single-target allocation and effective state; immutable events; current-allocation projection is transaction-only |
| `walkin_fee_versions`, `walkin_requests` | No table grants; create request via fixed public endpoint | Read/configure/confirm via Owner operation | Public request creates only server-priced provisional row; Owner confirmation only after JWT authorization |
| `attendance_checkins`, `attendance_payment_impacts`, `attendance_validity`, `attendance_validity_resolutions`, `offline_sync_submissions` | No table grants; public member check-in endpoint only | Read; submit provisional offline claims and separately resolve validity through Owner endpoint | Validates PIN/member or Owner sync, payment/allocation, membership, local date, uniqueness, and documented independent-payment resolution |
| `request_idempotency` | No grants | No direct access | Reserve/replay only within named operation; safe result excludes secrets and unnecessary PII |
| `cash_drawer_sessions`, `cash_reconciliations`, `cash_reconciliation_adjustments` | No grants | Read and invoke open/close/reconcile/correction operations | Recompute verified physical cash and append immutable close/adjustment atomically; keep income classification separate |
| `audit_events`, `audit_event_subjects`, `audit_chain_heads` | No grants | Read restricted audit view | Append-only event, typed subject links and chain-head write in same transaction as protected mutation |

The Owner endpoint must authenticate the Supabase access token and verify
`auth.uid()` against the one active `owner_access` row on every protected
operation. Never trust `user_metadata`, a client-supplied actor ID, or a stale
role claim. The Developer has no management Auth row, database role, project
membership, production secret, or routine live-data access; source-code access
does not grant runtime authorization. The Owner controls project membership,
production secrets and release approval.

Prefer `SECURITY INVOKER` for reads and operations safe under caller grants/RLS.
Use `SECURITY DEFINER` only for named, narrow transactions that need private
PIN, limiter, audit, or cross-table privileges. Public functions are owned by
`gym_public_executor`; Owner functions by `gym_owner_executor`. The separate
`gym_table_owner` does not execute calls. Executors have only required table
privileges and role-targeted policies, are `NOLOGIN`, `NOSUPERUSER`,
`NOBYPASSRLS`, have no caller role membership, and do not own tables. Use
`FORCE ROW LEVEL SECURITY` on private business tables. Define functions with
`SET search_path = ''` and schema-qualify every relation, type, and called
function, preventing caller-writable schemas and temporary objects from
shadowing names. Prohibit dynamic SQL. Revoke `EXECUTE` from `PUBLIC`
(including default privileges), then grant each function only to `anon` for
its single fixed-input public endpoint or `authenticated` for its Owner
endpoint. Every Owner operation verifies the signed caller JWT's `auth.uid()`
against active `owner_access`; never trust metadata or actor-ID input. Public
functions require the expected anonymous request role and accept no identity,
status, payment, price, or date facts from the client. RLS is defense in depth,
not a replacement for function authorization. No client gets direct DML to
business tables, projections, PIN material, audit tables, or valid attendance.

Public member check-in accepts only normalized identifier, PIN, and a
request/idempotency token over TLS. It performs rate limiting before expensive
hashing, constant-shaped generic responses and timing protections, no member
search/read endpoint, and no client-selected member UUID/status/payment/date.
Public walk-in creation accepts no amount, fee version, payment state, member
identity, attendance status or historical timestamp. Owner confirmation takes
an opaque request ID and method/evidence reference but reloads all authoritative
values and verifies the active Owner. Direct `attendance_checkins` insertion,
direct effective-payment changes, and forged `paid`/`valid` statuses are denied.

Where an Edge Function is used, it validates the caller JWT and forwards that
user-scoped JWT to a narrow RPC; it does not need a service-role key. Never
expose or log service-role credentials. Any future use requires separate Owner
approval and server-only storage plus request-level identity/Owner validation;
it is not the normal access model. No public function exposes generic SQL/table
access or unrestricted member/payment/attendance reads. Each privileged
transaction writes the mutation, projections, idempotency outcome, audit event,
typed subject FKs, and audit chain head atomically. Any audit, typed-reference,
chain-head, or idempotency persistence failure rolls back the protected change;
no success is returned before commit.
